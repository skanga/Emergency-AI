# Component Upgrades Implementation Plan

> Historical implementation plan, approved on 2026-11-25. Work was completed on `feature/component-upgrades` and merged into `main` at `d22579a`. Current procedures are in [the upgrade guide](../../upgrades.md); [standalone release validation](../../reviews/2026-11-25-standalone-release-validation.md) records the subsequent real upgrade/rollback/reapplication.

**Goal:** Explicit component checks/upgrades with preserved local content and offline recovery.
**Architecture:** Standard-library Python modules separate discovery, transactions, component staging and CLI/startup policy. Shell and batch launchers delegate and expose recovery before app imports.
**Tech Stack:** Python 3.8+, unittest, existing verified downloader/extractor, Git CLI.

## 1. Discovery
- [x] Add `tests/test_updates.py`: fake provider responses, installed identity, unknown/custom files, partial network failures, unchanged model family, matching ZIM editions.
- [x] Run `python -m unittest discover -s tests -p test_updates.py -v`; establish RED before adding `app/updates.py`.
- [x] Implement `inventory(root)`, `check(root, timeout=30)` returning JSON-safe component records (`component`, `status`, `installed`, `candidate`, `reason`). Candidates contain immutable identity and staged artifact metadata. No check runs downloaded code or mutates assets.
- [x] Repeat tests to GREEN. Bounded metadata requests; independent provider failures preserved.

## 2. Recovery foundation
- [x] Add `tests/test_upgrade_transaction.py` for successful activation/rollback, failure after each operation, newer user edits, path traversal/symlinks, backup retention and maintenance locking.
- [x] Establish RED with the same unittest discovery pattern.
- [x] Implement standalone `upgrade_recovery.py` containing `Transaction(root, component)`, `apply(changes, verify)`, `rollback(root, transaction_id)`, and `maintenance_lock(root)`. Changes map relative destination paths to staged files or None for removal. Persist before/after hashes, original modes and journal before mutation. Recover using retained immutable backups and refuse conflicting edits.
- [x] Test crash recovery and byte-identical original restoration. Check backup space before activation.

## 3. Component procedures
- [x] Add disposable Git and standalone fixtures in `tests/test_upgrade_app.py`. Test clean fast-forward, dirty/diverged refusal, exact baseline validation, local-file preservation, stale owned-file removal and rollback.
- [x] Implement `app/upgrade_app.py`: resolve immutable candidates, stage Git/source content, produce owned-file plans and verify candidate syntax/config. Standalone unknown baseline requires explicit baseline commit and matching owned files. Git activation uses fast-forward and recovery ref; rollback refuses subsequent edits.
- [x] Add `tests/test_upgrade_assets.py` for verified models, paired runtime assets, library supersession without backup retrieval and stage failure.
- [x] Implement `app/upgrade_assets.py`, reusing download/extract helpers but not `prepare.run`. Only apply supported verified candidates; explicit manual status for unknown/external dependencies. Verify runnable artifacts before activation. Keep prior weights/settings and old ZIM outside active folder.
- [x] Run component tests to GREEN, preserving evidence of RED.

## 4. CLI, startup and documentation

- [x] Implement `app/upgrade_cli.py` and thin dispatch in `emergency.py`. Add earliest recovery dispatch to launchers, before app imports; shared maintenance lock for prepare/start activation boundaries.
- [x] Add `docs/upgrades.md`: separate Git/standalone/model/runtime/driver/data procedures, inventory, backup storage, offline rollback and unknown-verification limitations. Link README and launcher help.

## 5. Verification and review
- [x] Run all Python tests and both Node suites; shell syntax and actual CLI help/checks.
- [x] Run disposable offline upgrade/rollback smoke tests. No changes to running installation or real model/ZIM assets.
- [x] Independently review spec compliance, then correctness/security/maintainability; fix required findings with regression tests.

## Implemented boundaries

Automated paths and verification are complete for the supported cases documented in `docs/upgrades.md`. Host drivers, missing integrity/provenance, foreign-platform execution, existing document indexes/source-policy migration and jointly incompatible dependency-group changes remain explicit manual procedures. Confirmation shows artifact download size; full temporary-space checks run during staging/activation. The initial implementation used disposable fixtures; later real installation/component validation and native CI are recorded in the review reports linked from the current upgrade guide.
